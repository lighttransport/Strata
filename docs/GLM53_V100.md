# GLM-5.3-Flash on Xeon Gold and Tesla V100

The mixed-quantization `UD-Q2_K_XL` model runs with its expert weights in
system RAM and a bounded expert cache on one or two Tesla V100 PCIe GPUs.
The measured dual-GPU configuration reaches **28.91 tok/s** for a 512-token
response with regular greedy decode, and **29.06 tok/s** with MTP depth 1.
A separate full-16K prompt configuration reaches **790.47 prefill tok/s**.
These results use the complete model, all layers and top-8 expert routing.

Measurements were collected on 2026-10-03–04.

## Hardware and software

| Component | Measured configuration |
| --- | --- |
| CPU | Two Intel Xeon Gold 6240 processors, 2.60 GHz nominal |
| CPU topology | 18 physical cores / 36 logical CPUs per socket; 36 physical cores / 72 logical CPUs total |
| Dual-GPU CPU configuration | 35 expert workers plus the host thread, across both sockets |
| Single-GPU CPU configurations | One socket's 18 physical cores / 36 logical CPUs; either 17 or 35 workers plus the host |
| System memory | 160 GiB available to the workload; host weight pages interleaved across both sockets |
| GPU | Two Tesla V100 PCIe 32 GB cards, SM70, PCIe Gen3 x16; single-GPU tests enable only one card |
| GPU memory limits | 32768 MiB per enabled card; capacity-proxy tests limit one card to 16384 or 15360 MiB |
| Build | Linux, GCC 12, CUDA 12.9, release build targeting SM70 |
| Model | All four GLM-5.3-Flash `UD-Q2_K_XL` GGUF shards |
| Allocated context | 131072 tokens, including prompt and response |

The single-GPU tests restrict CPU execution to one physical socket. They
retain interleaved memory across both sockets because this system cannot
hold the model in one socket's RAM alone. They therefore measure a
single-socket CPU allocation, rather than a standalone single-socket
machine with all memory attached locally. A single-socket machine with
sufficient RAM may have different memory bandwidth and latency.

## Model and memory

The inspected model has 45 main layers: 34 KDA and 11 sparse MLA layers,
three dense feed-forward layers and 42 mixture-of-experts layers. Each MoE
layer selects 8 of 288 experts. Hidden width is 4096 and expert intermediate
width is 2048. The quantization is a mixture of native formats, rather than
uniform two-bit weights.

| Tensor payload | Size |
| --- | ---: |
| Main expert weights | 99.03 GB |
| Main fixed weights | 6.89 GB |
| MTP draft block | 2.79 GB |
| Total tensor payload | 108.71 GB / 101.25 GiB |
| Selected main expert weights per decoded token before GPU-cache hits | 2.751 GB |

The timed runs keep byte-identical host weight pages resident using
`--lock-weights`. Loading and page locking are startup costs. The process
needs sufficient RAM and a sufficient locked-memory limit; the 160 GiB
workload allowance also covers mapped pages, pinned transfer buffers,
attention state and scratch. CPU weight prepacking is disabled.

A configured GPU budget includes a 1024 MiB runtime allowance. Automatic
cache admission also leaves scratch space, and the physical free-memory
guard remains enabled. Fixed projections, attention and routing stay on
the primary GPU. Resident routed experts execute on the enabled GPUs while
CPU workers handle cache misses. Expert weights retain their native bytes;
FP16 prefill temporarily dequantizes expert tiles into bounded scratch.

## Measurement method

All decode comparisons use the same **4096-token C++ coding prompt**, then
three 128-token requests and three 512-token requests in a resident process.
The untimed warmup and model startup are excluded. Decode throughput counts
`generated_tokens - 1` state advances. Prefill throughput includes request
reset and decode-cache preparation; it is reported separately from decode.
The table values are medians of the three measured requests.

The single-GPU matrix uses prefill batch 4096, the same 131072-token context,
automatic expert caching, adaptive cache replacement and regular greedy
decode for all configurations. Its 17-worker and 35-worker settings
compare physical-core use with SMT under the same socket affinity.

The long-prefill experiment uses the full **16384-token prompt in one
16384-token batch**, followed by three 2-token requests and three 512-token
quality responses. A 16K prompt's prefill rate is not the same workload as
the 4K decode fixture's prefill rate.

## Dual-GPU measurements

| Configuration | Prompt / prefill batch | CPU workers | Prefill tok/s | 128-token decode tok/s | 512-token decode tok/s |
| --- | --- | ---: | ---: | ---: | ---: |
| Regular greedy decode | 4096 / 8192 | 35 | 501.64 | 27.91 | **28.91** |
| MTP depth 1, batched resident verification | 4096 / 8192 | 35 | 292.37 | **29.45** | **29.06** |
| 16K prefill, 64-row bucket steps | 16384 / 16384 | 35 | 771.56 | — | 27.86 |
| Above with KDA column tiling | 16384 / 16384 | 35 | **790.47** | — | 27.52 |

The 16K prefill change improves prefill by 2.45%; its slightly lower decode
rate does not establish a decode improvement. MTP depth 1 gives little
long-response benefit on this fixture and has a higher preparation cost.
Regular greedy decode remains the straightforward reference configuration.
The earlier 40 decode tok/s and 1000 prefill tok/s targets are not reached.

## Single-GPU measurements and the 16 GB capacity proxy

All rows below were measured on one V100 **32 GB** card. The smaller budgets
simulate reduced cache capacity; they are not physical 16GB-card benchmarks.
CPU execution is restricted to one 18-core socket throughout.

| GPU budget | Workers + host | Prefill tok/s | 128-token decode tok/s | 512-token decode tok/s | Maximum sampled driver VRAM (MiB) |
| --- | ---: | ---: | ---: | ---: | ---: |
| 32768 MiB | 17 + 1 | 303.87 | 15.17 | **15.17** | 31,678 |
| 32768 MiB | 35 + 1 | 303.94 | 14.42 | **14.32** | 31,696 |
| 16384 MiB | 17 + 1 | 295.64 | 12.62 | **12.51** | 16,058 |
| 16384 MiB | 35 + 1 | 295.20 | 12.21 | **12.48** | 16,058 |
| 15360 MiB | 17 + 1 | 294.93 | 12.42 | **12.25** | 15,002 |
| 15360 MiB | 35 + 1 | 294.98 | 12.17 | **12.35** | 15,002 |

At the 32 GiB budget, 17 workers give the better long-decode result;
35 workers are 5.6% slower. At the smaller budgets, the long-decode rates
are close. These are comparisons of expert worker counts under the same
socket affinity, rather than evidence that more logical CPUs always help.

The 16 GiB-budget runs peak at 16,058 MiB of sampled driver VRAM. A physical
16GB card has less room for driver allocations and the retained free-memory
guard. The **15360 MiB budget** gives a more practical capacity proxy with
additional headroom. Driver samples are taken once per second and can miss
brief peaks; owned-allocation diagnostics are saved separately.

### Forecast for a physical Tesla V100 PCIe 16 GB

Using the 15 GiB-budget measurements as a conservative planning estimate:

| Same CPU allocation | Predicted 4K prefill tok/s | Predicted 512-token decode tok/s |
| --- | ---: | ---: |
| 17 workers + host, 18 physical cores | **about 295** | **about 12.3** |
| 35 workers + host, 18 physical cores | **about 295** | **about 12.3** |

This forecast assumes comparable GPU clocks and effective CPU/RAM bandwidth,
the same full model, 131072-token allocated context, batch 4096 and the same
cache policy. The physical 16GB variant was not tested. These numbers are
capacity-based estimates, not measured speed or a statistical confidence
interval for another card. The tested host memory remains interleaved across
two sockets even when CPU execution uses one socket.

Source: [generic measurement summary](glm53_flash_xeon_v100_measurement.json),
including individual trials, binary hashes, memory diagnostics and validation.

## Validation

The qualified dual-GPU decoder passed full-logit graph/direct comparisons,
eight-token sequential/batched verification and rollback checks. Repeated
64-token full-4K requests under Compute Sanitizer reported zero errors.
The full single-batch 16K KDA experiment also completed model memcheck with
zero errors and retained the reference's exact 512 generated token IDs.
The single-GPU 16384 MiB preflight used the full allocated context, a
three-token prompt, eight generated tokens and graph/direct comparisons;
its memcheck also reported zero errors. This small-prompt check is distinct
from the full-4K timing and coding validation.

KDA column tiling passed 60 component cases with exact output and retained
state bits, finite values and intact guards. The component sanitizer
reported zero errors. Its sample prepared 64-head, 64-token kernel measured
151.10 microseconds versus 213.12 microseconds for the original kernel;
that component gain is distinct from the end-to-end prefill gain.

The [single-GPU generated sources and validation summary](fixtures/glm53_xeon_v100_cpp_quality/README.md)
are included. Each completed reported coding response compiles as C++17 with
`-Wall -Wextra -Werror` and passes **400,532 independent oracle cases**.
Repeated token IDs are checked separately from behavioral quality. Cache
capacity changes can alter deterministic token IDs because CPU and GPU
expert arithmetic differ. These checks validate this fixture and the
changed mechanics, rather than broad model quality.

The cleanup build passes both CUDA parity suites and component memcheck.
It also reproduces the measured reference's exact 128- and 512-token outputs
on the full 4K prompt at the 16384 MiB budget with 17 workers, and its C++
response passes the same 400,532 cases. The Python regression suite passes
38 tests. Disabled, unqualified peer-buffer and lookup-snapshot prototypes
were removed; the validated KDA tiling path remains opt-in.

## Build and reproduce

Use the repository's pinned ggml dependency and an SM70-capable CUDA
installation. The measured build used CUDA 12.9 and GCC 12:

```sh
cmake -S . -B build-glm-v100 -G Ninja \
  -DSTRATA_ENABLE_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=70 \
  -DSTRATA_BUILD_TESTS=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build-glm-v100 -j 4 \
  --target strata-glm-decode glm_prefill_parity glm_kda_column_tiles_parity
python3 -m venv .venv-glm
.venv-glm/bin/pip install regex jinja2

export GLM_Q2_MODEL=/path/to/models/GLM-5.3-Flash-UD-Q2_K_XL-00001-of-00004.gguf
```

The other three shards must be alongside the first. Set the CUDA compiler
and host compiler explicitly in CMake if they are not the defaults.

The generic [V100 recipe](../tools/glm_v100.env) supplies the validated
opt-in kernel and cache settings. For the regular two-GPU decode fixture:

```sh
source tools/glm_v100.env
PYTHONPATH=tools numactl --interleave=all .venv-glm/bin/python \
  tools/glm_v100_bench.py "$GLM_Q2_MODEL" \
  docs/fixtures/glm53_cpp_quality/chat_prompt.txt \
  --decoder build-glm-v100/strata-glm-decode \
  --prompt-tokens 4096 --generated-tokens 128 --repetitions 3 \
  --validation-tokens 512 --validation-repetitions 3 \
  --context 131072 --threads 35 --gpu-devices 0,1 \
  --gpu-budget-mib 32768 --prefill-batch 8192 \
  --prefill-experts f16-batched --prefill-expert-cache-mib auto \
  --decode-prefill-cache --decode-cache-mib extend --decode-graphs \
  --decode-cache-window 256 --decode-cache-adapt \
  --output /tmp/glm-v100-two-gpu.json
```

For one GPU, unset `STRATA_GLM_PRIMARY_GROUPS`,
`STRATA_GLM_PREFETCH_GROUPS` and `STRATA_GLM_MLA_SPLIT`. Use
`--gpu-devices 0 --prefill-batch 4096`, set `--threads` to 17 or 35 and
choose budget 32768, 16384 or 15360. Use 15360 for the conservative
16GB-card profile. Restrict the process to the CPU IDs belonging
to the selected socket using `numactl --physcpubind=<socket-cpu-list>`;
CPU numbering varies by machine. Keep the memory policy explicit when
comparing results.

For the 16K prefill configuration, additionally set
`STRATA_GLM_F16_BUCKET_STEP=64` and `STRATA_GLM_KDA_COLUMN_TILES=1`, use a
16384-token prompt and prefill batch, and disable MTP/batched verification.
The single-GPU 16GB-budget configuration uses the smaller 4096-token batch.

The [generic server example](glm53_v100_server.example.json) uses placeholder
paths and binds to localhost. The GLM API is greedy text generation with
serialized requests; it does not cache conversation prefixes. For the
Threadripper 1950X measurements, see [the separate performance report](README_GLM53_FLASH.md).
