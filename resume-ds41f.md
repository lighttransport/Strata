# Resume: DeepSeek-V4.1-Flash on 2x V100

## Current TR16 decode handoff (2026-10-28)

This section supersedes the historical TR16 estimates and "lossless levers" below. The active target is single-sequence decode at least 30 tok/s, with 40+ as a stretch, preserving lossless behavior as much as possible; only after that is met, investigate batches below 64 and up to 4x throughput. It is **not achieved**. Earlier 39.71 tok/s used grouped GPU routing, deferred all CPU routes and top-two pruning; related same-tier measurements found mean KL 1.4256 and 58.6% top-1 agreement. Do not present that result as a qualified success. `IQ1S_FAST=1` also changed sampled model logits; use default IQ1_S arithmetic for an exact control.

On the RX 9070 XT / Threadripper 1950X / 128 GiB, the strongest sampled exact-output path uses the independent fixed 2,048 MiB tier, 15 threads, exact verification, yielding lane workers, grouped exact CPU routes, paired IQ1_S gate/up, and quota-3 CPU-order staging with ordered collection, host activation, a 192-slot frequency-ranked LRU cache and cached-only extras. It produced 9.30 tok/s on 600-code / 64 output and 9.81–9.90 on 600-text / 64 output, with exact greedy IDs. One 600-text / 128-output pair measured 9.49 versus unstaged exact 8.55, with all 128 IDs equal. Its teacher-forced captures matched exact logits byte-for-byte on 384 code positions and 728 held-out text positions, both including cache eviction. These narrow samples are not universal parity or a general performance guarantee. Seven-position history lookup reached 9.79 on the 128-output code sample and matched exact IDs but was slower on held-out text. Batch optimization has not been started because the single target is unmet.

Use `tools/ds41f_decode_guard.sh` for every GPU run, preserve its 2.5 GiB physical free-VRAM watchdog, 2 GiB desktop reserve, conservative 16 MiB per cache-slot preflight and systemd memory limits. The prior-boot OOM quarantine requires the user-authorized current-boot preflight scope, with runtime journal monitoring still active. The local model/draft paths and command flags appear in the TR16 section and subsequent experiment notes; raw captures and logs under `/tmp` are transient, not durable artifacts. No push is authorized. The worktree contains substantial pre-existing modifications and scratch; do not reset or clean it indiscriminately.

For the matched unstaged control omit the `STRATA_DS41_STAGE_*` switches and `STRATA_IQ1S_PAIR`; retain the same model, fixed profile, tier, prompt and output length. Do not set a profile derived from the evaluated output and describe it as independent. Capture mode, cache geometry, sample lengths and quality limitations are documented in the detailed chronological notes.

A final short-context test of `STRATA_DS41_GPU_TOPK_MIN=1` matched 128 held-out single-position logits and 1,024 GPU/host index selections, but measured 9.56 tok/s versus earlier 9.81–9.90 host-selection screens; code and long-context parity remain untested. The guard now bounds that threshold and offers an explicit selection diagnostic. Do not assume it is a speedup or generally equivalent.

The CPU expert path is the main bottleneck: a prior estimate put roughly 1.6–1.7 GB of expert weights per output token on CPU before current staging; event timings include overlap and are not pure kernel time. Staging, cache policy, paired dots, lookup, a separate GPU stream and multiple CPU scheduling variations have not produced the roughly threefold gain still needed. Next work should target a materially different exact expert execution/reuse strategy, with bounded buffers and explicit GPU/CPU synchronization, against the same fixed-tier exact control on independent prompts; measure full logits, token output, throughput and physical memory. Do not reintroduce the removed separate-stream, IQ2 pair or paired-down prototypes without new evidence. Rebuild affected HIP and CUDA backends and repeat the appropriate parity and guard checks before drawing conclusions.

**CPU/GPU activation-format boundary.** Static inspection confirms CPU expert Q8_K uses one float scale for 256 values, derived from the signed maximum, while the current GPU Q8_1 path uses a separate maximum and FP16 scale for each 32 values, with different rounding. Consequently, moving an expert to GPU changes its quantized input before any dot-product reduction. A bounded CPU-only synthetic check of 10,000 normally distributed 256-value blocks approximated those quantizers and found Q8_K / Q8_1 reconstruction relative L2 errors 0.00694 / 0.00534 and mutual relative L2 0.00805; 99.26% of reconstructed values differed. These are synthetic activation reconstruction measurements, not real model logits or a decomposition of GPU error; GPU dot reduction order and subsequent quantization can also differ. A parity-preserving offload would need to reproduce CPU Q8_K's 256-value signed scale, rounding, and dot/accumulation semantics on GPU, rather than feeding the current Q8_1 kernels. Any GPU prototype must retain the existing allocation, bounds, and physical VRAM guards and first validate small bounded data; no GPU run was made for this observation.

**IQ1_S codebook compatibility.** A CPU-only exhaustive comparison of the checked-in ggml tables confirmed all 16,384 grid values across 2,048 entries agree: the GPU nibble value minus one equals the CPU signed-byte value for each corresponding position. Thus a GPU implementation can reuse the existing GPU table to reconstruct the CPU grid. For default CPU arithmetic, each 256-value block accumulates eight independent integer lanes: lane `l` sums positions `4*l..4*l+3` in each 32-value sub-block, multiplying by `(8*grid + delta_sign) * (2*scale+1)`. Each lane then uses a separate float FMA with `half_scale * 0.125 * q8k_scale`; blocks remain in order, and the eight floating lanes are reduced with the CPU's `(0+4, 1+5, 2+6, 3+7)` followed by two pairwise horizontal adds. This mapping is derived from the AVX2 code, not yet independently tested as a GPU implementation; preserving CPU `sign_epi8` behavior and avoiding implicit FP reassociation also require care. No GPU work or speed claim was made by this table check.
